- `char *cmdline_copy` in `setup_stack()`: temporary writable copy used to tokenize the command line into arguments.
- `char *argv[MAX_ARGS]` in `setup_stack()`: temporary kernel array that records argument addresses before pushing `argv[]` onto the user stack.

#### ALGORITHMS

>A2: Briefly describe how you implemented argument parsing.  How do you arrange for the elements of argv[] to be in the right order?
>How do you avoid overflowing the stack page?

`process_execute()` receives the full command line, but `thread_create()` should use only the executable name as the thread name. Therefore I first copy the command line into a fresh page, then make another temporary copy and call `strtok_r()` on that second copy to extract the first token `prog_name`. The full original command line page is still passed to the child so that later stack setup can see all arguments.

Inside `load()`, I again make a temporary copy of the command line and use `strtok_r()` to extract the executable name before opening the file. This separates loading the executable from building the initial user stack.

Actual argument passing happens in `setup_stack()`. I allocate and map the top stack page, copy the whole command line into `cmdline_copy`, and tokenize it with `strtok_r()`. The resulting tokens are stored in `argv[]` in normal left-to-right order. Then I push the argument strings onto the user stack in reverse order, so after pushing, the strings appear in memory in a layout compatible with a normal `argv`.

After the strings are on the stack, I:

1. round the stack pointer down to a 4-byte boundary,
2. push a null sentinel for `argv[argc]`,
3. push the addresses of each argument in reverse order,
4. push the address of `argv[0]`,
5. push `argc`,
6. push a fake return address.

This preserves the expected left-to-right order when the user program reads `argv[0] ... argv[argc - 1]`.

To avoid stack overflow, every time I move the stack pointer downward I check whether it would go below `PHYS_BASE - PGSIZE`. If so, `setup_stack()` fails immediately. I also cap argument count with `MAX_ARGS` and keep all temporary command-line parsing within a single kernel page.

#### RATIONALE

>A3: Why does Pintos implement strtok_r() but not strtok()?

`strtok()` keeps its parsing state in hidden global static storage, so concurrent or nested tokenization can corrupt that shared state. Pintos kernels run multiple threads and may need reentrant parsing, so `strtok_r()` is safer because the caller provides the saved state explicitly.

>A4: In Pintos, the kernel separates commands into a executable name and arguments.  In Unix-like systems, the shell does this separation.  Identify at least two advantages of the Unix approach.

One advantage is separation of concerns: the kernel only executes programs, while the shell handles command parsing, quoting, escaping, pipelines, and redirection. This keeps the kernel smaller and simpler.

Another advantage is flexibility. Different shells can implement different parsing rules and user-facing features without changing the kernel at all.

A third advantage is security and robustness: complicated string parsing stays in user space, so parsing bugs are less likely to destabilize the kernel.

>B2: Describe how file descriptors are associated with open files. Are file descriptors unique within the entire OS or just within a single process?

Each process has its own `fd_list` and `next_fd`. When `open` succeeds, the kernel allocates a `struct file_descriptor`, stores the returned `struct file *` plus a fresh integer fd, and appends that record to the current thread's `fd_list`.

Therefore file descriptors are unique only within a single process, not globally across the entire OS. Two different processes may both have an fd `2`, but each `2` is looked up in that process's own list.

#### ALGORITHMS

>B3: Describe your code for reading and writing user data from the kernel.

I used a two-layer approach.

First, I validate user addresses before dereferencing them:

- `check_user_vaddr()` ensures a pointer is non-null, below `PHYS_BASE`, and currently mapped in the caller's page table.
- `check_user_buffer()` validates the first byte, last byte, and one address per page across a buffer range.

Second, I do the actual byte transfer with fault-tolerant helpers:

- `copy_in()` copies from user memory to kernel memory one byte at a time.
- `copy_out()` copies from kernel memory to user memory one byte at a time.
- `copy_in_string()` copies a user string into a newly allocated kernel page until `'\0'` or one page is reached.

These helpers use `get_user()` and `put_user()`, which are small inline assembly probes. In `page_fault()`, if the fault happened during one of these probes in kernel mode, the handler rewrites the saved registers so the probe returns `-1` instead of panicking the kernel. My syscall code then converts that failure into `sys_exit(-1)`.

For file I/O, I avoid passing raw user pointers directly to the file system. `sys_write()` copies user data into a kernel bounce buffer before calling `file_write()`, and `sys_read()` reads into a kernel bounce buffer and then copies the data back out to user memory.

>B4: Suppose a system call causes a full page (4,096 bytes) of data
>to be copied from user space into the kernel.  What is the least
>and the greatest possible number of inspections of the page table
>(e.g. calls to pagedir_get_page()) that might result?  What about
>for a system call that only copies 2 bytes of data?  Is there room
>for improvement in these numbers, and how much?

For a 4096-byte copy from user to kernel in my implementation:

- `check_user_buffer()` inspects the page table 3 times in the best case: first byte, last byte, and the page-start check in its loop. Since the range is exactly one page, these may all refer to the same page, but they are still separate calls.
- `copy_in()` then calls `check_user_vaddr()` once per byte before `get_user()`, so that adds 4096 more inspections.

Thus:

- least case for 4096 bytes: 4099 inspections,
- greatest case for 4096 bytes: also 4099 inspections.

For a 2-byte copy:

- `check_user_buffer()` does 3 inspections again: first byte, last byte, and loop check at offset 0.
- `copy_in()` adds 2 more, one per byte.

Thus:

- least case for 2 bytes: 5 inspections,
- greatest case for 2 bytes: also 5 inspections.

There is definitely room for improvement. A more efficient design could validate per page once, then copy a whole contiguous chunk inside that page without re-checking every byte. For a 4096-byte copy, that could reduce the cost from 4099 inspections to about 1 inspection for the page itself, or at least to O(number of pages) instead of O(number of bytes). For a 2-byte copy within one mapped page, it could also drop from 5 to about 1.

>B5: Briefly describe your implementation of the "wait" system call
>and how it interacts with process termination.

`wait` is implemented by `process_wait()`, which is called by the `SYS_WAIT` case in `syscall.c`.

When a parent creates a child in `process_execute()`, it also allocates a `child_process_status` record and links it into the parent's `child_processes` list. This record stores the child tid, exit status, whether loading succeeded, whether the child has exited, and two semaphores.

When the parent calls `wait(child_tid)`, `process_wait()`:

1. checks that the tid is valid,
2. searches the current process's `child_processes` list,
3. returns `-1` if the tid is not a direct child,
4. removes the child entry from the list immediately so a second `wait` on the same child fails,
5. blocks on `exit_sema` if the child has not exited yet,
6. reads the recorded `exit_status`,
7. releases the shared record reference and returns the exit status.

When a child exits in `process_exit()`, it writes its `exit_status` into `child_info`, marks `exited = true`, wakes a waiter with `sema_up(&exit_sema)`, and drops its own reference. This lets `wait()` either return immediately if the child already exited, or sleep until the child finishes.

>B6: Any access to user program memory at a user-specified address
>can fail due to a bad pointer value.  Such accesses must cause the
>process to be terminated.  System calls are fraught with such
>accesses, e.g. a "write" system call requires reading the system
>call number from the user stack, then each of the call's three
>arguments, then an arbitrary amount of user memory, and any of
>these can fail at any point.  This poses a design and
>error-handling problem: how do you best avoid obscuring the primary
>function of code in a morass of error-handling?  Furthermore, when
>an error is detected, how do you ensure that all temporarily
>allocated resources (locks, buffers, etc.) are freed?  In a few
>paragraphs, describe the strategy or strategies you adopted for
>managing these issues.  Give an example.

I tried to separate pointer safety from syscall logic. Rather than scattering raw page-table checks everywhere, I centralized most user-memory handling in helper functions such as `check_user_vaddr()`, `check_user_buffer()`, `copy_in()`, `copy_out()`, `copy_in_string()`, and `read_u32()`. As a result, the main syscall handlers can focus on the actual operation: decode arguments, validate/copy them through helpers, then perform the file-system or process action.

For example, `sys_write()` does not dereference the user buffer directly. It first validates the user range with `check_user_buffer()`, then copies each chunk into a kernel bounce buffer using `copy_in()`, and only then calls `file_write()`. This keeps the file-writing logic relatively clean while still guaranteeing that a bad user pointer kills the process.

For cleanup, I mostly rely on keeping resource ownership local and short-lived. Temporary strings returned by `copy_in_string()` are freed in the same syscall helper after use. File-system critical sections are wrapped tightly around the actual file-system call so locks are not held across unrelated work. For process loading, where cleanup is more complicated, I use a `goto done` style in `load()` so that all exit paths share one cleanup block that releases `filesys_lock`, frees temporary pages, and closes the executable on failure.

One concrete example is `copy_in_string()`: if probing the user string fails in the middle, it frees the allocated kernel buffer before calling `sys_exit(-1)`. Another is `load()`: regardless of which check fails, execution reaches the `done:` block that unlocks the file system and frees temporary resources consistently.

#### SYNCHRONIZATION

>B7: The "exec" system call returns -1 if loading the new executable
>fails, so it cannot return before the new executable has completed
>loading.  How does your code ensure this?  How is the load
>success/failure status passed back to the thread that calls "exec"?

In `process_execute()`, before creating the child thread, I allocate a shared `child_process_status` object and initialize `load_sema` to 0. The parent passes this shared object to the child through `process_start_info`.

In `start_process()`, the child stores that pointer into `cur->child_info`, calls `load()`, writes the result into `child_info->load_success`, and then performs `sema_up(&child_info->load_sema)`.

Meanwhile, after `thread_create()` succeeds, the parent immediately performs `sema_down(&child_info->load_sema)`. Therefore the parent cannot return from `exec` until the child has finished attempting to load the executable.

If loading failed, the child leaves `load_success == false`, the parent wakes up, observes that failure, removes the child from its list, releases the shared status, and returns `TID_ERROR` to the syscall layer, which becomes `-1` for `exec`.

>B8: Consider parent process P with child process C.  How do you
>ensure proper synchronization and avoid race conditions when P
>calls wait(C) before C exits?  After C exits?  How do you ensure
>that all resources are freed in each case?  How about when P
>terminates without waiting, before C exits?  After C exits?  Are
>there any special cases?

If `P` calls `wait(C)` before `C` exits, `process_wait()` finds `C`'s `child_process_status`, removes it from `P`'s child list so it cannot be waited on twice, sees that `exited == false`, and blocks on `exit_sema`. Later `C` exits, writes its exit status, sets `exited = true`, and does `sema_up(&exit_sema)`, which wakes `P`.

If `P` calls `wait(C)` after `C` has already exited, then `C` has already filled in the shared record and set `exited = true`. `process_wait()` still removes the record from the child list, but it skips blocking and returns the saved exit status immediately.

To free resources correctly in both cases, the shared record uses `ref_cnt = 2`, one reference for the parent side and one for the child side. The parent drops its reference either when `wait()` succeeds or when the parent exits without waiting. The child drops its reference during `process_exit()`. Whichever side exits last frees the record.

If the parent terminates before waiting, `process_exit()` iterates through its `child_processes` list and releases each remaining shared child record. The child still keeps its own reference through `cur->child_info`, so the status structure remains valid. When that child later exits, it publishes its exit code and drops the final reference, freeing the record safely.

If the parent terminates after the child has already exited but before calling `wait()`, the child has already dropped its reference, and the parent's `process_exit()` drops the remaining one while cleaning up the child list.

Special cases are:

- invalid tid: `wait()` returns `-1`,
- not a direct child: `wait()` returns `-1`,
- second `wait()` on the same child: returns `-1` because the record was removed on the first successful wait,
- child killed by the kernel: the exception path calls `sys_exit(-1)`, so the parent receives `-1` as the exit status.

#### RATIONALE

>B9: Why did you choose to implement access to user memory from the
>kernel in the way that you did?

I chose eager validation plus controlled copy helpers because it is straightforward and easy to reason about. Every user pointer is checked before use, and the actual transfer goes through small helper functions instead of open-coded dereferences spread across the syscall layer.

This design is less efficient than a fully fault-driven approach, because it may inspect the same page many times. However, for Project 2 it keeps correctness and debugging manageable. It also integrates well with the existing `get_user()`/`put_user()` mechanism and the modified page-fault path that turns a bad probe into a normal failure code.

>B10: What advantages or disadvantages can you see to your design
>for file descriptors?

The main advantage is simplicity. A per-process linked list of file descriptors is easy to initialize, extend, clean up on exit, and reason about. It also naturally matches the requirement that fds are process-local.

Another advantage is isolation: each process owns its own fd namespace, and closing all files on exit is just a list traversal.

The main disadvantage is lookup cost. `lookup_fd()` is a linear search, so every fd operation is O(number of open files). A table or hash-based design would be faster, but would also add more machinery than this project needs.

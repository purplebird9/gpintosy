#### ALGORITHMS

> A2: Briefly describe how you implemented argument parsing. How do you arrange for the elements of argv[] to be in the right order? How do you avoid overflowing the stack page?

**Parsing Strategy:**
1.  **Thread Creation:** In `process_execute()`, I copy the command line and use `strtok_r()` to extract just the program name to pass to `thread_create()`.
2.  **Loading:** In `load()`, I extract the executable name again to open the file.
3.  **Stack Setup:** In `setup_stack()`, I tokenize the full command line into `argv[]`.

**Stack Layout:**
To ensure correct memory layout, I push items onto the user stack in the following order:
1.  **Argument Strings:** Pushed in reverse order (right-to-left).
2.  **Word Alignment:** Round stack pointer down to a 4-byte boundary.
3.  **Null Sentinel:** Push `0` for `argv[argc]`.
4.  **Argument Addresses:** Push the addresses of the strings in reverse order, so `argv[0]` sits at the lowest address.
5.  **`argv` Pointer:** Push the address of `argv[0]`.
6.  **`argc`:** Push the total argument count.
7.  **Return Address:** Push a fake return address (`0`).

**Avoiding Overflow:**
In `setup_stack`, every time before moving down the stack pointer, I check if it goes below `PHYS_BASE - PGSIZE`. If it does, `setup_stack()` fails immediately. 
I also enforce `MAX_ARGS` to bound the parsing space.

#### RATIONALE

> A3: Why does Pintos implement strtok_r() but not strtok()?

`strtok()` stores its parsing state in a hidden global variable, making it unsafe for concurrent parsing in a multithread kernel. 
`strtok_r()`, which uses a caller-provided state variable to ensure reentrancy and thread safety.

> B2: Describe how file descriptors are associated with open files. Are file descriptors unique within the entire OS or just within a single process?

When `open` succeeds, the kernel allocates a `struct file_descriptor`, pairs the `struct file *` with a fresh integer (from `next_fd`), and appends it to the thread's `fd_list`. 

Therefore, file descriptors are **unique within a single process**. For example, two processes can both have an FD `2`, but each maps to a different file in its own list.

> B3: Describe your code for reading and writing user data from the kernel.

I use a two-layer approach:

1.  **Validation:** `check_user_vaddr()` and `check_user_buffer()` ensure pointers are non-null, below `PHYS_BASE`, and mapped in the page table.
2.  **Safe Transfer:** I use helper functions (`copy_in`, `copy_out`, `copy_in_string`) that transfer data byte-by-byte using inline assembly probes (`get_user`/`put_user`). If a probe faults, the modified `page_fault()` handler catches it, safely sets the return value to `-1`, and my syscall layer terminates the process with `sys_exit(-1)`.

For file I/O, I use **kernel buffer**. 
`sys_write` copies user data into a kernel buffer  (in a time to avoid output disorder) before calling `file_write()`.
`sys_read` reads into a kernel buffer before copying out to user memory.

> B5: Briefly describe your implementation of the "wait" system call and how it interacts with process termination.

**Syscall Wait:**
Implemented by calling `process_wait()`.
`process_wait`:
1. check that the tid is valid,
2. search the current process's `child_processes` list,
3. returns `-1` if the tid is not a direct child,
4. remove the child entry from the list immediately (so a second `wait` on the same child fails)
5. block on `exit_sema` if the child has not exited yet,
6. read  `exit_status`,
7. free  the shared record reference and return exit status.

**Interaction:**
1.  **Setup:** During `exec`, the parent allocates a `child_process_status` struct, links it to its `child_processes` list, and shares it with the child.
2.  **Wait:** When the parent calls `wait(tid)`, it finds the record. It removes the record from the list immediately (preventing duplicate waits) and blocks on `exit_sema`.
3.  **Exit:** In `process_exit()`, the child writes its exit status to the record, sets `exited = true`, and calls `sema_up(&exit_sema)`.
4.  **Completion:** The parent wakes up, reads the exit status, returns.

> B6: Any access to user program memory at a user-specified address can fail due to a bad pointer value. Such accesses must cause the process to be terminated... How do you best avoid obscuring the primary function of code in a morass of error-handling? Furthermore, when an error is detected, how do you ensure that all temporarily allocated resources (locks, buffers, etc.) are freed?

**Strategy for Clean Logic:**
I decouple pointer safety from syscall logic by centralizing memory access into robust helpers (`check_user_buffer`, `copy_in_string`, `read_u32`). The syscall handlers simply decode arguments, call the copy helpers, and perform the OS action. If a helper detects a bad pointer, it terminates the process internally, keeping the main syscall body clean.

**Strategy for Cleanup:**
I rely on short-lived local resource ownership and a `goto done` pattern. 
*   *Example (Strings):* `copy_in_string` allocates a kernel buffer. If a page fault occurs mid-copy, it frees the buffer locally before calling `sys_exit(-1)`.
*   *Example (Load):* In `load()`, if any step fails, execution jumps to a single `done:` label that consistently releases `filesys_lock`, frees temporary pages, and closes the executable.

#### SYNCHRONIZATION

> B7: The "exec" system call returns -1 if loading the new executable fails, so it cannot return before the new executable has completed loading. How does your code ensure this? How is the load success/failure status passed back to the thread that calls "exec"?

Synchronization is handled via a `load_sema` inside the shared `child_process_status` struct.
1.  The parent creates the child and immediately calls `sema_down(&load_sema)`.
2.  The child runs `load()`, writes the bool into `load_success`, and calls `sema_up(&load_sema)`.
3.  The parent wakes up, checks `load_success`. If false, it removes the child, cleans up the record, and returns `-1`.

> B8: Consider parent process P with child process C. How do you ensure proper synchronization and avoid race conditions when P calls wait(C) before C exits? After C exits? How do you ensure that all resources are freed in each case? How about when P terminates without waiting, before C exits? After C exits? Are there any special cases?

**Synchronization:**
*   **P waits before C exits:** P blocks on `exit_sema`. C eventually exits, updates the status, and wakes P.
*   **P waits after C exits:** C has already updated the status and `sema_up`. P's `sema_down` passes immediately, fetching the result.

**Resource Management (by Reference Counting):**
The shared record uses `ref_cnt = 2` (one for P, one for C). The struct is only freed when `ref_cnt` reaches 0.
*   **P waits successfully:** C drops its ref on exit. P drops its ref after reading the status. P frees the record.
*   **P exits before C:** P drops refs for all children in its list. C continues running and drops its ref after it exits. C frees the record.
*   **P exits after C (no wait):** C drops its ref on exit. P drops the final ref during its `process_exit()` cleanup.

**Special Cases:**
*   Invalid TID, non-direct child, or double-waiting: `wait()` immediately returns `-1`.
*   C killed by kernel exception: Exception handler forces `sys_exit(-1)`, so P correctly receives `-1`.

> B9: Why did you choose to implement access to user memory from the kernel in the way that you did?

I chose eager validation combined with byte-by-byte copy helpers because it prioritizes simplicity, correctness, and ease of debugging over raw performance. It integrates cleanly with Pintos' `get_user`/`put_user` design. While it results in redundant page table lookups, it prevents subtle memory corruption and keeps the syscall implementation highly reliable for lab2.

> B10: What advantages or disadvantages can you see to your design for file descriptors?

*   **Advantages:** A per-process linked list is extremely simple to implement, initialize, and clean up. It naturally enforces process-level isolation for FDs.
*   **Disadvantages:** Lookup performance is $O(N)$. For processes with many open files, searching the linked list on every `read`/`write` will be slower than an array or hash-table design.

timer_sleep(ticks) :
- 首先关闭中断,进入临界区;
- 通过 start + ticks 计算出该线程应当唤醒的时间 wakeup_ticks。

timer_interrupt_handler():
- 在每个tick, 定时器中断处理程序会被调用。
- 遍历 sleep_list，检查其中每个线程的 wakeup_ticks。
- 如果当前全局 ticks 大于或等于线程的 wakeup_ticks，说明该线程睡眠时间已到，将其从 sleep_list 中移除，并调用 thread_unblock() 将其移入就绪队列。
- 最后调用 thread_test_yield() 检查是否需要发生抢占。(donation)

>A4: How are race conditions avoided when multiple threads call
>timer_sleep() simultaneously?

在 timer_sleep() 中，修改 sleep_list 和调用 thread_block() 之前，使用了 intr_disable() 关闭了所有中断, **禁用了线程的上下文切换（禁止了抢占）**, 让{计算wakeup时间, 加入sleep_list, 阻塞线程} 成为单个线程的原子操作。这保证了多个线程调用时, 线程 A 的操作不会被线程 B 打断，A 和 B 的调用变成了严格的串行。

#### ALGORITHMS

>B3: How do you ensure that the highest priority thread waiting for
>a lock, semaphore, or condition variable wakes up first?

- **Waiters list**: sema->waiters 和 cond->waiters存放的是BLOCKED的线程。我放弃了对它们list_insert_ordered, 不按顺序维护这些表，因为被BLOCKED的线程也可能会donation而动态改变其priority。相反，在 sema_up() 或 cond_signal() 中准备唤醒线程之前，我会使用 list_sort 配合自定义的比较函数（priority_compare / cond_priority_compare）对waiters按优先级降序排序。随后list_pop_front() 即可确保取出优先级最高的线程。


最高优先级线程"wake up"之后: 
- **Ready List**: 存放的是 READY 状态的线程。在 `thread_unblock` 和 `thread_yield`中，统一使用 `list_insert_ordered` 以priority降序将线程插入 ready_list。调度时直接 `list_pop_front` 即可获取最高优先级线程。由于调度器总是无脑 list_pop_front(&ready_list)，所以 ready_list 必须时刻保持有序。

- **thread_test_yield**: 我实现了一个 `thread_test_yield()` 函数。每当一个线程被解除阻塞时（例如在 `sema_up` 之后或计时器到期时），或者当当前运行线程的优先级降低时，`thread_test_yield()` 会将当前线程的优先级与 `ready_list` 队首线程的优先级进行比较。如果新唤醒的线程具有更高的优先级，当前线程会立即让出 CPU。

>C2: How is the way you divided the cost of scheduling between code
>inside and outside interrupt context likely to affect performance?

- **在中断上下文中（Inside Interrupt Context）：** 在 timer_interrupt() 中处理所有周期性的重计算任务。每 4 个 ticks 遍历全局线程队列（all_list）更新所有线程的优先级；每 100 个 ticks 再次遍历更新所有线程的 recent_cpu 和系统的 load_avg。
- **在非中断上下文中（Outside Interrupt Context）：** 处理由系统调用或线程主动行为引发的属性改变，例如 thread_set_nice() 更新 nice 值；以及就绪队列的维护，如 thread_yield() 和 thread_unblock() 时使用 list_insert_ordered 将线程按优先级插入就绪队列。

**对系统性能的潜在影响**

- **负面影响（中断延迟增加）：** 定时器中断处理程序运行时，会隐式关闭外部中断。由于我将重新计算所有线程的 priority、recent_cpu 和 load_avg 放在了中断上下文中执行，这就构成了一个 `O(N)`的操作。每次进行定点数运算都会消耗 CPU 周期。当系统内存在大量线程时，中断处理程序的执行时间会被显著拉长，增加**系统的中断延迟（Interrupt Latency）**，这可能导致系统对键盘、磁盘等其他外部硬件中断的响应变慢。
- **正面影响（维护就绪队列的开销最小化）：** 我没有在时钟中断中直接对 ready_list 进行全局重排序，而是把排序的开销分散转移到了线程进入就绪状态的那一刻（通过 list_insert_ordered，其时间复杂度为 `O(R)`。因为多数时候非运行状态的线程优先级变化不需要立即体现在队列顺序中，这种“将复杂的入队排序操作分摊到中断外部或线程状态切换时”的设计，有助于防止中断处理程序过度膨胀。

我创建了一个抽象层，将定点数运算的底层实现封装在了自定义的头文件 threads/arithmetic.h 中。通过定义一系列宏（Macros）来处理定点数操作（如 INT_TO_FP, ADD_FP, MUL_FP_INT, DIV_FP_INT 等)。

为什么选择使用宏（Macros）构建抽象层？

- **高可读性与语义清晰**：MLFQS 的调度公式（例如 recent_cpu 和 load_avg 的计算）非常复杂。如果将位移操作（如 << 14, >> 14）硬编码散布在 thread.c 中，代码将变得极其冗长且难以阅读。通过宏，计算逻辑 FP_TO_INT_ZERO(ADD_FP_INT(DIV_FP_INT(t->recent_cpu, -4), PRI_MAX - t->nice * 2)) 直接映射了数学公式，逻辑一目了然。
    
- **零函数调用开销（Zero Overhead）**：由于优先级的重新计算发生在硬件时钟中断处理程序（timer_interrupt）中，系统每隔几个 ticks 就需要大量执行这些计算。如果使用普通函数（Functions）来实现抽象，高频的函数调用会导致栈帧的反复创建与销毁。而宏在预处理阶段直接内联展开，不产生任何函数调用开销，保证了中断处理程序的高效执行。
    
- **高可维护性**：它将定点数的核心参数（如小数位数 f = 1 << 14）隔离在一个独立的文件中。如果未来系统需要更高的精度（例如改为 15.16 格式），只需在 arithmetic.h 中修改宏定义即可，无需改动任何 thread.c 的核心调度代码，极大降低了出错的风险。

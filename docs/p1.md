#### ALGORITHMS

>A2: Briefly describe what happens in a call to timer_sleep(),
>including the effects of the timer interrupt handler.

**timer_sleep(ticks) :**
- 首先关闭中断,进入临界区;
- 通过 `start + ticks` 计算出该线程应当唤醒的时间 `wakeup_ticks`。
- 将当前线程插入到全局的 `sleep_list` 链表尾部。随后调用 `thread_block()` 阻塞当前线程,
- 退出临界区, 恢复之前的中断状态。

**timer_interrupt_handler():**
- 在每个tick, 定时器中断处理程序会被调用。
- 遍历 `sleep_list`，检查其中每个线程的 `wakeup_ticks`。
- 如果当前全局 `ticks` 大于或等于线程的 `wakeup_ticks`，说明该线程睡眠时间已到，将其从 `sleep_list` 中移除，并调用 `thread_unblock()` 将其移入就绪队列。
- 最后调用 `thread_test_yield()` 检查是否需要发生抢占。(donation)




>A3: What steps are taken to minimize the amount of time spent in
>the timer interrupt handler?

之前的唤醒是朴素的 `O(n)` `sleep_list` 遍历;
新实现将 `sleep_list` 插入换成 `list_insert_ordered`，保证 `sleep_list` 按照苏醒时间降序。
中断处理程序只需检查链表头部即可在 `O(1)` 时间内完成。

#### SYNCHRONIZATION

>A4: How are race conditions avoided when multiple threads call
>timer_sleep() simultaneously?

在 `timer_sleep()` 中，修改 `sleep_list` 和调用 `thread_block()` 之前，使用了 `intr_disable()` 关闭了所有中断, **禁用了线程的上下文切换（禁止了抢占）**, 让{计算 `wakeup` 时间, 加入 `sleep_list`, 阻塞线程} 成为单个线程的原子操作。这保证了多个线程调用时, 线程 A 的操作不会被线程 B 打断，A 和 B 的调用变成了严格的串行。


>A5: How are race conditions avoided when a timer interrupt occurs
>during a call to timer_sleep()?

通过 `timer_sleep()` 核心代码段保持关中断，等于**屏蔽了硬件的异步打断**。保证在线程 A 完成sleep的全部操作之前，定时器中断根本无法触发，从而保证了“写者”（`timer_sleep`）和“读者/写者”（`timer_interrupt`）之间的互斥。

>A6: Why did you choose this design?  In what ways is it superior to
>another design you considered?

- 此设计摒弃了原始代码中的“busy-waiting”，通过阻塞休眠线程bing将其放入 `sleep_list`，CPU可以释放给其他有用的进程。  
- 相比于维护多个定时器队列，维护单一的全局 `sleep_list` 逻辑清晰，实现简单，且易于调试。

>B2: Explain the data structure used to track priority donation.
>Use ASCII art to diagram a nested donation.  (Alternately, submit a
>.png file.)

**Data structure**
为了实现优先级捐赠，在 `struct thread` 中新增了以下成员：
- `base_priority`：记录被捐赠前的真实优先级。释放锁后，用于恢复该原始值（或剩余捐赠中的最高值）。
- `donors_list`：捐赠者链表，记录所有向当前线程捐赠了优先级的线程。
- `donors_elem`：专属链表节点。用于将当前线程插入到锁持有者的 `donors_list` 中（因为线程可能同时在就绪或等待队列中，不能复用普通的 `elem`）。
- `waiting_on_lock`：记录当前线程因哪把锁而被阻塞。用于回溯锁的持有链条，从而实现 `nested donation`.

**Nested donation scenario:**  
Thread A (Priority 61) wants Lock 1. Lock 1 is held by Thread B.  
Thread B (Base Priority 32) wants Lock 2. Lock 2 is held by Thread C.  
Thread C (Base Priority 31) is currently running.  
Due to nested donation, C inherits 61 from A via B.
```
+---------------------+
 |      Thread A       |
 | Base Priority: 61   |
 | Curr Priority: 61   |
 | donors_list: (empty)|
 | waiting_on_lock: -----------------+
 +---------------------+             |
       | (donors_elem)               v
       |                      [ Lock 1 ]
       |                      holder: Thread B
       v
 +---------------------+
 |      Thread B       |
 | Base Priority: 32   |<---- (A is in B's donors_list, B priority becomes 61)
 | Curr Priority: 61   |
 | waiting_on_lock: -----------------+
 +---------------------+             |
       | (donors_elem)               v
       |                      [ Lock 2 ]
       |                      holder: Thread C
       v
 +---------------------+
 |      Thread C       |
 | Base Priority: 31   |<---- (B is in C's donors_list, C priority becomes 61)
 | Curr Priority: 61   |
 | waiting_on_lock:NULL|
 +---------------------+
```


#### ALGORITHMS

>B3: How do you ensure that the highest priority thread waiting for
>a lock, semaphore, or condition variable wakes up first?

- **Waiters list**: `sema->waiters` 和 `cond->waiters` 存放的是 `BLOCKED` 的线程。我放弃了对它们 `list_insert_ordered`, 不按顺序维护这些表，因为被 `BLOCKED` 的线程也可能会 `donation` 而动态改变其 `priority`。相反，在 `sema_up()` 或 `cond_signal()` 中准备唤醒线程之前，我会使用 `list_sort` 配合自定义的比较函数（`priority_compare` / `cond_priority_compare`）对 `waiters` 按优先级降序排序。随后 `list_pop_front()` 即可确保取出优先级最高的线程。


最高优先级线程"wake up"之后: 
- **Ready List**: 存放的是 `READY` 状态的线程。在 `thread_unblock` 和 `thread_yield` 中，统一使用 `list_insert_ordered` 以 `priority` 降序将线程插入 `ready_list`。调度时直接 `list_pop_front` 即可获取最高优先级线程。由于调度器总是无脑 `list_pop_front(&ready_list)`，所以 `ready_list` 必须时刻保持有序。

- **抢占逻辑**: 我实现了一个 `thread_test_yield()` 函数。每当一个线程被解除阻塞时（例如在 `sema_up` 之后或计时器到期时），或者当当前运行线程的优先级降低时，`thread_test_yield()` 会将当前线程的优先级与 `ready_list` 队首线程的优先级进行比较。如果新唤醒的线程具有更高的优先级，当前线程会立即让出 CPU。



>B4: Describe the sequence of events when a call to lock_acquire()
>causes a priority donation.  How is nested donation handled?

当线程 A 尝试获取已被线程 B 持有的锁 `lock` 时：
1. MLFQS检查(MLFQS不需要donation)
2. 调用 `intr_disable()` 关中断，以确保后续修改等待队列和捐赠列表的操作是原子的。
3. A发现锁被占用, 设置自己的 `waiting_on_lock = lock`。
4. A 将自己（使用 `donors_elem`）按优先级降序插入到 B 的 `donors_list` 中。
	- *这里是无条件加入的。即使当前线程优先级较低，也必须加入，因为它的优先级未来可能会被其他线程提升，从而引发连锁反应*
5. 调用 `thread_nested_donation()` 进行嵌套捐赠
6. A开中断并调用 `sema_down` 阻塞自己。
7. 当锁被B释放，A被调度唤醒后，再次关闭中断, 将 `cur->waiting_on_lock` 置为 `NULL`（不再等待），并将自己设为锁的新持有者 `lock->holder = cur`，最后恢复中断。

辅助函数 `thread_nested_donation`: 从当前线程向上回溯，通过检查 `cur->waiting_on_lock` 找到锁拥有者，若拥有者的优先级小于捐赠者，则提升拥有者的优先级。该过程循环递归进行，直到到达没有等待锁的线程，或者达到最大深度（设置为 8）以防止死锁导致死循环。


>B5: Describe the sequence of events when lock_release() is called
>on a lock that a higher-priority thread is waiting for.

1. MLFQS检查
2. 关中断
3. 当前线程调用 `thread_recall_donation(lock)`
	- 将所有正在等待*当前被释放的这个锁* 的线程（包括那个高优先级线程）从自己的 `donors_list`（捐赠者列表）中移除。
	- 重新计算自己的优先级。此时，如果当前线程没有持有其他被高优先级线程等待的锁，它的有效优先级将降回其原本的基础优先级（`base priority`）；如果还持有其他锁，则降回剩余捐赠者中的最高优先级。
4. 解除锁占用 (`lock->holder = NULL`) 并调用 `sema_up` 唤醒最高优先级等待者, 加入到 `ready_list`.
5. 执行 `thread_test_yield()`。由于在第 3 步中当前线程的优先级已经降低，而在第 4 步中那个高优先级线程刚刚被加入了就绪队列，当前线程会发现就绪队列首部的线程优先级高于自己现在的优先级。因此，当前线程会立刻主动yield。

#### SYNCHRONIZATION

>B6: Describe a potential race in thread_set_priority() and explain
>how your implementation avoids it.  Can you use a lock to avoid
>this race?


**竞态条件：**
在 `thread_set_priority()` 中，当一个线程（假设为线程 A）尝试修改自己的优先级并更新捐赠列表时，存在以下潜在的并发竞争场景：

- 线程 A 正在执行 `thread_set_priority()`。它刚刚修改了 `cur->base_priority`，正在执行 `list_sort(&cur->donors_list, ...)` , 或者正在读取 `max_donor->priority`。
- 此时发生了一个时钟中断, 调度线程 B 运行。
- 线程 B 运行后，调用 `lock_acquire()` 试图获取一个正被线程 A 持有的锁。由于锁不可用，线程 B 触发了优先级捐赠逻辑：它执行 `list_insert_ordered(&A->donors_list, ...)` 将自己插入线程 A 的捐赠队列，并修改线程 A 的 `priority`。
- 当线程 A 恢复运行时，它仍在执行之前的 `list_sort` 过程，但底层的链表结构已经被线程 B 在另一处修改了。这会导致链表指针错乱、引发 Page Fault，或者导致线程 A 的优先级计算出错误的值。

**解决方案：**
应在 `thread_set_priority() `的核心操作（修改优先级、对 donors_list 排序及取值）之前，调用` intr_disable()` 关闭了外部中断，并在操作完成后恢复中断状态。

**不能使用锁。** 原因：
1. **死锁与循环依赖** 如果引入一个 `priority_lock` 来保护线程的优先级更新，当线程调用 `lock_acquire(&priority_lock)` 时，如果该锁被占用，线程需要被阻塞等待，这又会触发新一轮的优先级捐赠逻辑。而新的优先级捐赠又需要去获取这个 `priority_lock`。这就构成了“为了处理锁的优先级机制，而去请求一个依赖优先级机制的锁”，导致无限递归或死锁。
2. **中断上下文限制** 锁的底层实现是信号量，如果获取不到锁，线程会睡眠, 而中断上下文中不允许睡眠。尽管 `thread_set_priority` 本身不在中断中被调用，但线程优先级的读取和调度判断经常发生在中断上下文中。如果用锁来保护这些数据结构，一旦中断处理程序需要访问它们，就可能导致内核 Panic。因此，只能使用最低级的同步原语——关中断 (`intr_disable`)。

#### RATIONALE

>B7: Why did you choose this design?  In what ways is it superior to
>another design you considered?

- **分离 `elem` 和 `donors_elem`**: 因为一个线程既需要存在于等待队列（或就绪队列）中，又需要存在于拥有者的捐赠列表中。如果共用同一个 `list_elem` 会引发链表损坏（Kernel Panic)。
- **thread_test_yield** 统一的抢占逻辑函数, 方便各种场景需要检查抢占的时候调用. 我本来在 `thread_create` 等函数里单独写了一个比较抢占的逻辑, 但是不够统一而且太麻烦了
- **list_sort:** 如果只在 `sema_down` 插入时用 `list_insert_ordered` 排序，线程在等待期间，其优先级可能会由于被捐赠而发生动态变化, 导致需要唤醒是list不是有序的. 因此放弃 `insert_ordered`, , 而是在唤醒前调用 `list_sort`, 强制排序来保证此时的优先级是latest且降序的，确保绝对正确的唤醒顺序。
- 当线程由于锁被占用而阻塞时，我选择**无条件**将其加入到锁holder的 `donors_list` 中。即使当前线程的优先级低于 holder 的优先级，也照加不误。之前的设计是“条件插入”，即只有当 `cur->priority > holder->priority` 时，才将其加入 `donors_list` 的设计。它没有考虑 `BLOCKED` 的线程优先级也可能变化, 因此任何线程都有”潜力“捐赠，需要无条件加入 `donors_list`. 
- 将 `list_insert` 放在 `lock_acquire` 中, 而不是在 `thread_nested_donation` 函数内部。当前线程作为**直接等待者**加入当前锁 holder 的 `donors_list`，并且**仅此一次**，易于维护而且方便 `recall_donation` 的实现

>C2: How is the way you divided the cost of scheduling between code
>inside and outside interrupt context likely to affect performance?

**对性能的影响:**
- **负面影响（增加中断延迟）：** 
  我将周期性的全局重计算（如每 4 tick更新 `priority`，每 100 tick更新 `recent_cpu`）放在了**interrupt context**中执行。这是一个 `O(N)` 的遍历操作，且包含密集的定点数运算。当系统线程数激增时，会显著拉长中断处理程序的执行时间，导致系统对键盘、磁盘等其他外部硬件中断的响应变慢。
- **正面影响（平摊排序开销）：** 
  不在中断中对 `ready_list` 进行暴力的全局重排。而是在**outside interrupt context** 处理由系统调用或线程主动行为引发的属性改变，例如 `thread_set_nice()` 更新 `nice` 值；以及 `ready_list` 的维护，如 `thread_yield()` 和 `thread_unblock()` 时使用 `list_insert_ordered` 将线程按优先级插入就绪队列。这种设计避免了中断处理程序的进一步膨胀，同时保证了调度器获取最高优先级线程始终是高效的 `O(1)` 操作。

#### RATIONALE

>C3: Briefly critique your design, pointing out advantages and
>disadvantages in your design choices.  If you were to have extra
>time to work on this part of the project, how might you choose to
>refine or improve your design?

**Advantages:**
- **逻辑清晰、一致性高：** 集中在时钟中断中执行定时更新，保证了系统中所有线程属性计算的同步性，不易出现状态不一致的 bug。
- **调度成本低：** 剥离了就绪队列排序与时钟中断的耦合，调度器 `next_thread_to_run()` 始终能以极低的开销弹出首节点。

**Improvements:**
- **实时维护队列有序（取代被动重排):** 目前每次唤醒都要用 `list_sort` 刷新, 而我想抛弃 `sort` 的开销, 实现队列实时的有序。比如，当一个 `blocked` 或者 `ready` 的线程 `priority` 变化的时候, 立即将其从原链表中 `remove`，再用 `list_insert_ordered` 重新插入。确保所有的等待队列在任何瞬间都是实时且绝对有序的。
- **引入Lazy计算减少中断延迟：** 取消时钟中断里的全局遍历。在中断中仅更新正在 `running` 的线程状态；对于 `blocked` 的线程，将其属性的计算**推迟**到它们被唤醒进入非中断上下文时，再进行时间跨度的补偿计算。这能彻底根除中断里 `O(N)` 的开销，大幅提升系统响应速度。

>C4: The assignment explains arithmetic for fixed-point math in
>detail, but it leaves it open to you to implement it.  Why did you
>decide to implement it the way you did?  If you created an
>abstraction layer for fixed-point math, that is, an abstract data
>type and/or a set of functions or macros to manipulate fixed-point
>numbers, why did you do so?  If not, why not?

我创建了一个抽象层，将定点数运算的底层实现封装在了自定义的头文件 `threads/arithmetic.h` 中。通过定义一系列宏（Macros）来处理定点数操作（如 `INT_TO_FP`, `ADD_FP`, `MUL_FP_INT`, `DIV_FP_INT` 等)。

使用宏（Macros）的原因: 
- **高可读性与语义清晰**：MLFQS 的调度公式（例如 `recent_cpu` 和 `load_avg` 的计算）非常复杂。如果将位移操作（如 `<< 14`, `>> 14`）硬编码散布在 `thread.c` 中，代码将变得极其冗长且难以阅读。通过宏，计算逻辑 `FP_TO_INT_ZERO(ADD_FP_INT(DIV_FP_INT(t->recent_cpu, -4), PRI_MAX - t->nice * 2))` 直接映射了数学公式，逻辑一目了然。
- **零函数调用开销（Zero Overhead）**：由于优先级的重新计算发生在硬件时钟中断处理程序中，系统每隔几个 `ticks` 就需要大量执行这些计算。如果使用普通函数来实现抽象，高频的函数调用会导致栈帧的反复创建与销毁。而宏在预处理阶段直接内联展开，不产生任何函数调用开销，保证了中断处理程序的高效执行。
- **高可维护性**：它将定点数的核心参数（如小数位数 `f = 1 << 14`）隔离在一个独立的文件中。如果未来系统需要更高的精度（例如改为 `15.16` 格式），只需在 `arithmetic.h` 中修改宏定义即可，无需改动任何 `thread.c` 的核心调度代码，极大降低了出错的风险。
